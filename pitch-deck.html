The Solution

Mathematics Replaces Trust

1

Creator Encrypts Locally

Browser generates an AES-256 key via Web Crypto API. Prompt text is encrypted to ciphertext, uploaded to IPFS. The key never leaves the browser unencrypted.

2

Key is FHE-Encrypted On-Chain

The 256-bit AES key is split into two 128-bit halves. Each half is encrypted by the CoFHE SDK to an InEuint128 with a ZK proof of well-formedness. Stored on Sepolia as euint128 ciphertexts.

3

Purchase Atomically Grants Access

One transaction: pay ETH → contract verifies → calls FHE.allow(keyHandle, buyer). The ACL update and payment are inseparable. No trusted third party involved.

4

Buyer Decrypts in Browser

CoFHE SDK decrypts both key halves using buyer's wallet. Keys are concatenated, IPFS ciphertext is downloaded, AES-GCM decrypts plaintext. Secret material never touches a server.

CORE USP

The AES key never exists in plaintext anywhere except the buyer's browser

🚫
Not on-chain — only euint128 ciphertexts stored
🚫
Not in any API — no server decrypts or relays
🚫
Not in event logs — key handles are opaque ciphertexts
🚫
Not in localStorage — ephemeral CryptoKey object only
✅
Only in the authorised buyer's active session — mathematically enforced, not promised

// ─── LISTING: Creator uploads key halves ─── function listPrompt( InEuint128 calldata encryptedKey0, InEuint128 calldata encryptedKey1, // ... title, category, CID, price ) external { // 1. Verify ZK proof — ciphertext is well-formed euint128 kp0 = FHE.asEuint128(encryptedKey0); euint128 kp1 = FHE.asEuint128(encryptedKey1); // 2. Contract retains persistent ACL access // (required to re-grant on future purchases) FHE.allowThis(kp0); FHE.allowThis(kp1); // 3. Creator can verify their own listing FHE.allowSender(kp0); FHE.allowSender(kp1); l.keyPart0 = kp0; l.keyPart1 = kp1; } // ─── PURCHASE: Atomic payment + key grant ── function purchasePrompt(uint256 listingId) payable { // ... payment validation ... // 4. Permanent, irrevocable ACL grant FHE.allow(l.keyPart0, msg.sender); FHE.allow(l.keyPart1, msg.sender); }
🧮
FHE.asEuint128()

ZK-Proof Validated Encryption

Accepts InEuint128 — a client-encrypted ciphertext bundled with a zero-knowledge proof that proves correctness without revealing the value.

🔗
FHE.allowThis()

Contract-Persistent ACL

Grants the contract itself future permission to call FHE.allow() on these handles across transactions — the mechanism that makes gated re-granting possible.

🎯
FHE.allow(handle, addr)

Atomic Payment-Gated Access

Called inside purchasePrompt. Payment check and ACL grant are in the same transaction — atomicity is guaranteed by the EVM. No race condition possible.

♾️
Permanent ACL

Irrevocable Ownership

FHE.allow cannot be undone. Buyers own access forever — even if the creator delists. Enables trustless resale semantics by design.

Architecture

Hybrid AES-256 + FHE — Best of Both Worlds

Layer 1 — Content
AES-256-GCM
Encrypts prompt text (any length)
Layer 2 — Key Gate
FHE (CoFHE)
Encrypts AES key as 2 × euint128
Content Storage
IPFS / Pinata
Ciphertext public — useless without key
Key Storage
Sepolia Chain
euint128 × 2 — never plaintext
Listing Flow (Creator)
prompt_text → AES-256-GCM → ciphertext → IPFS
AES key (256b) → split → key0 (128b) + key1 (128b)
CoFHE.encrypt(key0) → InEuint128
CoFHE.encrypt(key1) → InEuint128
listPrompt(InEuint128 × 2, CID, price) → on-chain euint128 × 2
Purchase Flow (Buyer)
purchasePrompt(id, value=price) → EVM tx
FHE.allow(euint128, buyer) × 2 — atomic
getKeyHandles(id) → euint128 handles
CoFHE.decrypt(handle0, handle1) → k0 + k1
reconstruct → AES key → AES-GCM decrypt → plaintext
Why split the key?  FHE operates on euint128 — max 128 bits of plaintext per handle. AES-256 requires 256 bits. Splitting into two halves is the minimal overhead to store a full AES key on-chain as FHE ciphertexts.

Why FHE?

FHE vs. Every Alternative

❌ Without FHE

🏢

Centralised Marketplace

Platform stores prompts in plaintext. Any data breach, insider, or subpoena exposes every seller's IP.

🤝

Commit-Reveal Protocol

Seller can refuse to send key, send wrong key, or collude with escrow. Trust assumption never goes away.

🔌

MPC / TEE Approaches

Require honest majority among MPC nodes or trust in hardware manufacturer (Intel SGX). Off-chain complexity with on-chain pretense.

📋

NFT-Gated Links

Decryption key sent to NFT holder via off-chain API. The API can be queried by anyone who reverse-engineers the call or gets the server logs.

✅ With FHE (PromptVault)

🧮

Contract Computes on Ciphertext

The smart contract grants access to an encrypted value — it never decrypts. No plaintext key exists anywhere except buyer's browser.

⚛️

EVM Atomicity = Perfect Atomicity

Payment and FHE.allow() happen in one transaction. Either both succeed or both revert. No window for a race condition.

✍️

ZK-Proof on Upload

FHE.asEuint128(InEuint128) verifies a ZK proof that the ciphertext is well-formed and was created by the caller — on-chain, no oracle needed.

🔏

Platform Cannot Read Anything

Even PromptVault's own deployer address cannot read a prompt. The ACL is enforced by CoFHE's cryptographic layer, not by code we wrote.

FHE is the only approach that lets the smart contract act as an access-control authority over encrypted data without ever holding or seeing the plaintext. Every other model either trusts a party (seller, platform, TEE vendor) or exposes the key during transfer. PromptVault's USP is the elimination of that trust — not a reduction of it.
